# Review, controlled comparison and scoped acceptance

**Ownership:** SHARED_CONTRACT. **Maturity:** proposed method and optional pilot procedures; static illustrations do not prove operational effectiveness.

## Independent critique and proportional depth
Separate stakeholder intent from a suggested solution. Understand the user task, critique risks, consult relevant evidence/references, compare options including retaining the current solution, recommend, then record the actual decision and its limits.

A reversible local presentation change can need a short review; interaction/navigation changes need scenario evidence; permissions, privacy, business identity, destructive effects or high uncertainty need deeper source and failure analysis. These review depths do not introduce task states or replace required QA.

Pair review requires actual independent contributions. Record consensus, dissent and deferral without simulating another person's opinion. Designer agreement, product acceptance, permission to mutate and empirical validation remain different outcomes. Ask only the smallest unresolved question after recovering existing evidence; batch external questions when appropriate and never send without authorization.

## Controlled comparison
Fix the actor, audience, dataset, domain object, source version and viewport. Vary only the stated condition; show expected effects, assumptions and negative cases. If another dimension changes, disclose it or redesign the comparison.

A configuration toggle illustration is not the resulting audience's experience. A drawing of an authorized view does not demonstrate filtering or enforcement. Use the [comparison seed](../templates/CONTROLLED_COMPARISON.md) and keep requirements, proposals and test execution separate.

## Acceptance has scope
Record the deliverable and acceptance criteria before execution. Distinguish document prepared, static scene inspected, interactive prototype exercised, application behavior tested and stakeholder acceptance. An explicitly accepted design scope may close that design unit while unresolved technical work stays visible; it cannot mark the entire task complete if its criteria require those tests.

A waiver records its authority, exact criterion/scope, reason, duration and residual risk. It does not turn an unexecuted test into PASS, create a standing waiver or silently advance reporting cursors. Preserve the project's existing task-state vocabulary.

Separate formal task completion numerator/denominator, candidate visual coverage, source inventory coverage and test coverage. Counts from unlike scene sizes or different source snapshots are not comparable progress metrics. Reconcile aggregate mirrors with the owner ledger and immutable source commit.

## Deliverable-first and phase pilots
Choose an authorized material unit with a clear finish condition, execute it, verify it, persist proportionately and continue with the next independent unit. Investigate again only after new evidence, contradiction or changed scope. Measure completed units and real blocked causes before claiming efficiency.

Build/prototype/consolidated-QA sequencing and reversible MVP proposals are optional locally authorized pilots. Representing a labeled hypothesis does not authorize real permission enforcement, backend effects or rollout. Optional test automation can be deferred without waiving required acceptance tests. A local blocked decision should not stop independent work.

Use [acceptance cases](../templates/ACCEPTANCE_CASES.md) in the existing owner record. Do not create another status store or claim a pilot passed because its proposal was approved.
