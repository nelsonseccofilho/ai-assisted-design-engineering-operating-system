# Compatible design changes and consumer adoption

**Ownership:** SHARED_CONTRACT. **Maturity:** proposed reusable procedure informed by documented implementation/readback cases; no claim of universal migration safety.

## Preflight and smallest change
Inspect the live canonical inventory before creating or swapping assets. Compare API, variants, property names/defaults, slot semantics, label ownership, selected/disabled states, dimensions, constraints, tokens and accessibility. A canonical replacement can still be incompatible with a legacy consumer.

An unlabeled control plus a sibling label is not equivalent to a labeled canonical control: a blind swap can duplicate text and alter height. Hiding a symptom, detaching an instance or substituting a visually similar local copy does not repair source conformance.

For shared API/foundation changes, document the exact bounded proposal, existing behavior, affected consumers, alternatives, compatibility risks, approval and rollback/repair approach before mutation. Reuse existing authority; this procedure grants no new permission. Prefer additive opt-in variants/properties that retain prior defaults when the evidence supports that approach.

## Verify the actual component structure
Linked parents do not validate inserted slot content. Inspect custom text, containers and actions independently. Preserve source keys, intentional overrides and semantic bindings when changing approved scope. Distinguish natural full-content design views from constrained runtime viewport behavior; HUG and Fixed dimensions at different ancestor levels can produce different outcomes.

Check property references, used/unused exposed properties and uniqueness of variant combinations. Repair a publication defect narrowly, preserving meaningful IDs and established APIs. Do not rename or delete a historical variant merely to clear a warning.

## Publication and adoption are separate facts
1. Verify the source change and its owner history.
2. Verify the actual publication result. A source edit or asset repair does not prove publication.
3. Import/update the published component in affected consumers only within authorized scope.
4. Reconcile instance links, properties, overrides, content, states, interactions, layout and annotations after synchronization.
5. Record consumer adoption separately from source publication, linking the two owner records.

A successful library publication does not prove that every consumer updated. Inspect the real publication UI or supported publication response when required; do not infer it from an API screenshot. Recheck inherited annotations and instance content after updates.

## Maturity pilot
Journey validation → local organization → generic promotion → consumer adoption is an optional staged experiment until the complete chain is demonstrated in representative cases. Reuse canonical assets throughout. Do not abstract an unvalidated product pattern or import a product's permissions into another domain.

Use the [migration seed](../templates/COMPONENT_MIGRATION.md). Existing release, shared-library and consumer acceptance gates remain.
