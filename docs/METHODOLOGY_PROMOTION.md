## Pilot acceptance before stronger claims

For each pilot, use the [private review seed](../runtime/docs/templates/METHOD_REVIEW.md) to record the scoped hypothesis, baseline, actual execution, limits and accountable reviewer. Select representative cases including an unresolved high-impact decision. Check fresh-context recovery without inventing consensus or approvals. Compare delivered units, time/reads, duplicate work and observed failures before claiming efficiency.

For component maturity, demonstrate the complete chain through published-component consumer adoption, preserved properties/states and affected-consumer QA. For annotation/layout pilots, inspect native labels and expanded notes visually; bounding boxes alone are insufficient. For handoff, separate contextual retrieval, visual construction and functional completeness. For language choices, review zero/one/multiple counts separately from ratios, capacity labels, domain terminology and absence messages.

Keep optional tool automation separate from required acceptance criteria. An unavailable automation tool may permit delivery for review with NOT RUN limitations; it does not waive functional or security gates.

## Publication gates

Before public writes, review the complete proposed content, filenames, commit and PR text. Remove private identities, people, locators, node/file/change/task IDs, media/transcripts, quotes and unique combinations that could reconstruct a project. A company-name substitution alone is insufficient.

Run package, synchronization and methodology regressions; review privacy/secret checks and read back every changed file at the resulting immutable commit. Record hosted checks independently. An earlier infrastructure disposition is not a standing waiver for this PR. Keep a Draft PR while required live/pilot gates lack evidence; do not merge, release, update private pins or claim successful adoption without their own gates.
